1. OVERVIEW
-------------------------------------------------------------------------------
Misuc is a small native Linux DAW: a Qt 6 widget app ("Fusion" style) driving a
lock-free PipeWire audio engine behind a versioned JSON project format. There
is NO plugin architecture and NO signal bus/routing graph — the audio path is
flat tracks -> master. Everything that is scoped for the current milestone
chain is implemented, tested, and green (54145 engine checks + 213 UI harness
checks). Remaining "Beyond" items (buses, VST3/LV2 hosting) are NOT started and
the audio graph has been deliberately kept simple so they can be added later
without a redesign.

3. MIXER AUDIT
-------------------------------------------------------------------------------
Implementation is real and engine-backed, not decorative:
- Model owns mixer params (Track.gainDb/pan/mute/solo) so they persist and are
  export-honoring.
- MixerPage::syncToEngine -> AudioEngine::publishMixer (triple-buffered,
  RT-safe, applied per block with anti-zipper smoothing on the audio thread).
- Meters come from the engine's per-track post-gain ChannelMeters polled at
  30 Hz by the UI (MixerPage::pollMeters).
- Export flows through the same per-track gain/pan/gate + master, so the bounce
  matches what you hear (verified in test_mixer.cpp).

Gaps / caveats:
- Master fader runs live (engine_.setMasterGainDb) but is NOT stored on the
  Session, so a per-session master level is not persisted (resets to 0 dB each
  session). Track params ARE persisted.
- Solo = "any solo present" logic; correctly exclusive but there is no UI
  affordance beyond toggling (no "clear solo").
- Strip colors are a fixed 8-color wheel rotated by index (not user-settable).
- QLayout warning "mixerHost already has a layout" on rebuild (cosmetic,
   harness-only; strips are deleteLater'd before re-layout).
- Intermittent harness-only flake was seen ONCE at Phase 12 (mixer undo +
   selection checks failed a single run), then passed 4 of the next 4 runs;
   not reproduced today (populated harness margin - none, ALL OK x doubles).

4. SIGNAL PATH AUDIT
-------------------------------------------------------------------------------
Live (PipeWireBackend::process callback -> AudioEngine::process):
   input -> monitor gain (pre-master) + input meter; record capture (mono,
   only while playing)
   MIDI score (triple-buffered, per-track) + audio clips (per-track) ->
     per-track stereo scratch -> smoothed gain L/R (constant-power pan) ->
     per-track post-gain meters -> mute/solo gate -> SUM to output
   starting counters: tempo/click/groove rendered into output while playing;
     count-in renders while Counting.
   metronome/groove + master switch -> master gain smoother -> master meters.
Record path: 0.5*(L+R) mono capture is independent of the mixer; the monitor
mix is added pre-master at monitor gain. So recording what you hear is exact;
the track mixer never affects the captured bytes (documented behaviour).
Export shares process() with looping off and count-in off (AudioEngine::
renderToWav, chunked 512 frames, float WAV).
Threading: UI -> lock-free SPSC control queue (1024); audio thread never
allocates/locks; the score/clip/mixer triple-buffer pattern with ref counts is
used for all published state.

5. BUSES / ROUTING AUDIT
-------------------------------------------------------------------------------
STATUS: NOT IMPLEMENTED (by explicit scope decision — the user ordered this
frozen until the audit completes).
- No `bus`/`busId`/`send`/`return`/`aux` concept anywhere: Buses grep across
  engine and ui sources only matches comments/doc text ("master bus" wording).
- The only summing stages are the implicit track-gate sum into the output
  buffer and the master-gain pass. No per-track -> bus routing structure, no
  return tracks, no send slopes.
- NOT REQUIRED to redesign: the per-track render loop already renders each
  track into its own fixed stereo scratch (scratchL_/scratchR_), the natural
  injection point for a later send/group matrix; master metering is a single
  stage; session schema can gain a "buses" array without a version bump need
  (additive field + migration tolerance in v2 reader).
- Recommendation on resume: add `std::vector<Bus>` to Session (gain/pan/mute/
  solo sends per track, post-fader or pre-fader per send), a bus summing stage
  after the per-track stage and before master, publish via a like
  publishBusMixer triple-buffer. No change to the per-track engine core.

11. FILE / ASSET PATH AUDIT
-------------------------------------------------------------------------------
- Loading: Session::fromJson validates schema; MainWindow::openProject calls
  resolveAssets(dir) right after load so clips play after reopen.
- Saving: writeProject serializes a RELATIVIZED COPY (Session::relativizeAssets)
  — the live session keeps absolute paths; the file on disk stores
  `audio/tone.wav` under the project folder. Paths outside the folder (and
  already-relative ones) are left untouched.
- Staging: imports and recordings are copied/written into <project>/audio/.
- Round-trip verified by unit tests (session_clip_paths_roundtrip,
  session_clip_paths_external_assets_stay_absolute) and by the harness
  (Phase 14: write project, assert JSON has "audio/tone.wav", reopen, assert
  resolved absolute sourceFile).
- Caveats: relativize/ resolve are string-path based (strip trailing "/",
  prefix match) — no filesystem canonicalization (symlinks/case/relative
  project dirs rely on the caller passing an absolute path); resolveAssets
  does not expand "~" references (documented as out of scope).
